# nissan/ — Nissan Leaf 전용 진단 모듈 (1차 버전에서는 비활성)

## 2026-08-04 실차 결과 — 통신은 된다

**결론이 뒤집혔다.** 아래 2026-08-03 조사는 "게이트웨이가 막고 있을 것"이라고 봤지만,
실제로는 **요청 주소를 지정하지 않은 것**이 원인이었다.

ECU 응답 스캔(`ATSH` + 표준 UDS 읽기)을 2019 Leaf 에서 실행한 결과
**23개 주소가 응답했다.**

```
700 70F 72D 72E 735 73E 760 762 763 764 765
76D 772 778 77D 78C 793 79A 7B6 7BA 7BB 7BD 7D5
```

- 방송 주소(`7DF`)로 보낸 표준 OBD 요청은 여전히 전부 `NO DATA` — Leaf 가 표준 PID 를
  구현하지 않는다는 점은 사실이었다.
- 그러나 **개별 주소로 보낸 ISO 14229 표준 요청에는 응답한다.**
- 확인된 조합: 프로토콜 `ATSP6`, 헤더 `ATSH<주소>`, 흐름 제어 `ATFCSH/ATFCSD/ATFCSM`

### 실제로 읽어 낸 오류코드 (2026-08-04, 흐름 제어 적용 후)

| ECU | 코드 | 상태 | 해석 |
|---|---|---|---|
| `79A` | **P3180-97** | 0x0B | 현재 고장 + 이번 주기 고장 + 확정 |
| `79A` | **P317E-97** | 0x0B | 현재 고장 + 이번 주기 고장 + 확정 |
| `7BB` | **P33ED-00** | 0x0C | 보류 + 확정 |
| `764` | B2630-11, B2631-15, B27A0~B27A4-79 | 0x10 | 삭제 후 검사 미완료 (현재 고장 아님) |

`P317E` / `P3180` 은 공개 자료에서 **리튬이온 배터리 계통** 코드로 언급된다.
정확한 정의는 Nissan 정비 매뉴얼이 필요하며, 이 앱은 추측 설명을 넣지 않는다.

`764` 응답은 첫 수집 때 연속 프레임 하나(순번 25)가 유실되어
뒷부분 코드가 잘못 해석되었다. 이 사례가 프레임 유실 감지 기능을 넣은 계기다.

### 실제로 수집한 응답 (검증 자료)

| ECU | 요청 | 응답 | 해석 |
|---|---|---|---|
| `7BB` | `1902FF` | `59 02 0E 33 ED 00 0C` | P33ED-00, 확정+보류 |
| `79A` | `1902FF` | `10 0B 59 02 0F 31 80 97` | 2건 (첫 프레임) |
| `764` | `1902FF` | `10 33 59 02 19 A6 30 11` | 약 12건 (첫 프레임) |
| `700` | `22F190` | `10 14 62 F1 90 …` | 차대번호 응답 |
| `70F` 외 다수 | `1902FF` | `59 02 xx` | 코드 없음 |

이 응답들은 **추측이 아니라 실제 차량에서 받은 것**이며,
`UdsDtcParserTest` 에 그대로 검증 자료로 들어가 있다.

### 여전히 넣지 않은 것

여기서 쓰는 것은 전부 **ISO 14229 국제 표준 읽기 서비스**다.
Nissan 전용 service `0x21` 이나 제조사 고유 DID 는 여전히 넣지 않았다.
그건 아래 조건을 만족해야 한다.

## 2026-08-03 조사 결과 — 왜 표준 OBD로는 안 되는가

실제 2019 Leaf 에서 표준 OBD 조회가 **전부 `NO DATA`** 로 나온 뒤 공개 자료를 조사했다.
결론은 앱의 결함이 아니라 차량의 구조였다.

1. **Leaf 는 표준 OBD PID 를 지원하지 않는다.**
   내연기관이 아니라 배출가스 규제 대상이 아니므로 OBD-II 표준 PID 준수 의무가 없다.
   Mode 01/03/07/0A 가 `NO DATA` 로 오는 것이 정상 동작이다.
   출처: <https://leaf-obd.readthedocs.io/en/latest/tutorial/elm327.html>

2. **2018년 이후(ZE1) 는 OBD-II 포트가 CAN 게이트웨이로 분리되어 있다.**
   브로드캐스트 CAN 트래픽이 포트까지 오지 않으며, 게이트웨이는 점화가 꺼지면 전원이 내려간다.
   실제 CAN 을 보려면 계기판 뒤 게이트웨이 배선을 직접 탭해야 한다(8선 케이블 필요).
   출처: <https://docs.openvehicles.com/en/latest/components/vehicle_nissanleaf/docs/index.html>

3. **진단 데이터는 UDS 유사 요청으로만 얻을 수 있다.**
   표준 UDS 0x22 가 아니라 **service 0x21** 을 쓰는 Nissan 변형이며,
   ISO-TP 다중 프레임으로 응답한다. LeafSpy 가 이 방식을 쓴다.

4. 확인된 프로토콜은 **ATSP6 (ISO 15765-4 CAN 11bit/500kbps)** 이다.
   실제 차량에서 6·7 은 버스 오류 없이 `NO DATA`, 8·9 는 `CAN ERROR` 가 났다.

### 그래서 무엇이 부족한가

전용 진단을 구현하려면 **ECU 주소(CAN ID)와 요청 바이트열**이 필요하다.
포럼과 리버스 엔지니어링 위키에 후보가 돌아다니지만, 아래 조건을 아직 만족하지 못한다.

- 공식 정비 매뉴얼(FSM) 근거 없음
- 실제 차량에서 검증한 응답 로그 없음 (지금 이 차량은 통신 자체가 안 됨)
- 모델·연식별 차이가 크다고 여러 곳에서 경고

따라서 **추측한 주소를 코드에 넣지 않는다.** 아래 조건은 그대로 유효하다.

## 현재 상태

**이 패키지에는 실제 CAN 명령이 하나도 들어 있지 않습니다.**
인터페이스와 이 문서만 존재하며, 기능 플래그 `NissanLeafService.ENABLED = false` 로 잠겨 있습니다.

이유는 단순합니다. 확인되지 않은 ECU 주소, 진단 세션 명령, 보안 접근 키를
추측해서 차량에 보내면 다음 위험이 있습니다.

- 고전압 계통이 예상치 못한 상태로 전환될 수 있음
- 에어백 · ABS 모듈이 비정상 상태로 남을 수 있음
- ECU가 잠기거나 정비소 재프로그래밍이 필요해질 수 있음
- 삭제해서는 안 되는 진단 이력이 사라져 원인 추적이 불가능해짐

## 추가할 수 있는 조건

아래 중 **하나 이상**이 확보되기 전에는 어떤 전용 명령도 추가하지 않습니다.

- [ ] Nissan 공식 정비 매뉴얼(FSM)의 해당 진단 절차
- [ ] 합법적으로 사용할 수 있는 공개 프로토콜 자료
- [ ] 실제 LeafSpy 로그와의 충분한 교차검증
- [ ] 실제 차량에서 취득한 읽기 전용 CAN 로그
- [ ] 검증된 ECU 주소와 응답 형식
- [ ] 테스트 차량에서 안전하게 반복 검증한 결과

인터넷 게시글에서 가져온 명령을 근거 없이 복사하는 것은 위 조건에 해당하지 않습니다.

## 추가할 때의 규칙

1. 표준 OBD 모듈(`obd/`)과 완전히 분리한다.
2. 기능 플래그로 기본 비활성 상태를 유지한다.
3. **읽기 전용 기능부터** 구현한다.
4. ECU별 명령은 코드가 아니라 데이터(테이블)로 관리한다.
5. 각 명령마다 출처와 검증 상태를 주석으로 남긴다.
   ```
   // 출처: (문서명 / 로그 파일 / 날짜)
   // 검증: (검증 방법 / 검증 차량 / 반복 횟수)
   ```
6. 삭제 기능은 읽기 기능과 별개의 추가 승인 절차를 거친다.
7. 위험 ECU(에어백, ABS, 브레이크, 고전압 배터리 제어)는 **기본적으로 삭제 기능을 제공하지 않는다.**

## 참고: 표준 모듈이 이미 하는 일

| 기능 | 위치 | 비고 |
|---|---|---|
| Mode 03 저장 DTC | `obd/ObdService` | 표준 |
| Mode 07 보류 DTC | `obd/ObdService` | 표준 |
| Mode 0A 영구 DTC | `obd/ObdService` | 표준 |
| Mode 04 삭제 | `obd/ObdService` | 배출가스 관련만, 이중 확인 필요 |

Nissan Leaf의 EV 전용 오류(VCM, LBC, OBC/PDM)는 위 표준 명령으로
읽히지 않을 수 있습니다. 이는 앱의 결함이 아니라 표준 OBD-II의 범위 문제입니다.
